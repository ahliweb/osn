# ADR-0002: Bun + TypeScript + Zod toolchain

## Status

Accepted, 2026-09-05.

## Context

ADR-0001 establishes that this repository is curriculum-as-code: a
schema, a domain model, and CLI/render tooling over validated data. TR-01
in `docs/requirements/register.md` requires "a strict TypeScript + Bun
toolchain (typecheck, lint, format, test scripts) that succeeds on a clean
clone, as the mechanical precondition for the §13 Quality Review of every
later artefact." A runtime, a validation library, and a test/build
toolchain all need to be chosen once, early, because every later issue
(#9 onward) is written against them.

## Options considered

1. **Node.js + `tsc` + a separate test runner (Vitest/Jest) + a separate
   validation library.** The conventional TypeScript stack: Node as the
   runtime, `tsc` for compilation, a dedicated test framework, `npm`/`pnpm`
   for package management.
2. **Python + Pydantic.** A strong, widely-used data-validation library
   (Pydantic) with static type hints, on a mature, widely-taught runtime.
3. **Plain JSON Schema + ajv.** Validate the curriculum JSON against
   hand-written JSON Schema documents using `ajv`, with TypeScript types
   maintained separately (or generated by a codegen step) for the domain
   layer.
4. **Bun + TypeScript + Zod.** Bun as the single runtime, package manager,
   bundler, and test runner; TypeScript in strict mode for the domain and
   CLI code; Zod as the schema library, whose schemas are simultaneously
   the runtime validator and the source of inferred static types (see
   ADR-0003).

## Decision

Option 4: Bun + TypeScript + Zod, as already reflected in
`package.json` (`zod` dependency, `@types/bun`, `typescript`), `tsconfig.json`
(`strict: true`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`),
`bunfig.toml` (coverage config), and `.github/workflows/ci.yml` (pinned
Bun version). This is already implemented (TR-01, issue #1, done); this
ADR records why.

### Why option 1 (Node + tsc + Jest/Vitest) was rejected

More moving parts for the same outcome: a separate test framework
(Vitest or Jest) with its own configuration file and plugin ecosystem, a
separate transpile step (`tsc` or `ts-node`/`esbuild`) before anything
runs, and a separate package manager and lockfile format. Bun collapses
runtime, package manager, bundler (`bun build`), and test runner
(`bun:test`) into one binary with one lockfile (`bun.lock`) and no
transpile step — TypeScript runs directly. For a project whose actual
deliverable is curriculum content and not build tooling, minimising the
number of independently-versioned tools to keep in sync is a direct
reduction in maintenance surface, and Bun's test runner and bundler are
measurably faster in practice, which matters for a CI pipeline that runs
on every push and PR (`docs/development/ci-cd.md`).

### Why option 2 (Python + Pydantic) was rejected

Pydantic is a strong validation library with real type-hint integration,
and would satisfy the validation requirement on its own merits. It was
rejected because it means running two toolchains for one project: this
repository would need both a Python environment (interpreter version,
virtualenv or equivalent, `pip`/`poetry` lockfile) and, eventually, a
TypeScript one anyway if any consumer wants typed access to the corpus
from a JS/TS platform (the more likely target for an LMS/dashboard, per
ADR-0001's "what a consumer must build themselves"). There is no ecosystem
reason to introduce a second language runtime into a repository this
size; it would double the CI matrix, the linting configuration, and the
onboarding burden for every future contributor for no capability this
project needs that Zod does not already provide.

### Why option 3 (JSON Schema + ajv) was rejected

JSON Schema plus `ajv` validates data correctly, but the schema and the
TypeScript types describing that data are two separate artefacts that
must be kept in sync by hand (or by a codegen step, which is another
moving part). Zod schemas are simultaneously the runtime validator and
the source of inferred static types (`z.infer<typeof Schema>`) — see
ADR-0003 for why that single-source-of-truth property matters for this
repository's domain layer specifically. Choosing ajv would mean every
schema change requires remembering to update a parallel `.d.ts` file (or
running a generator step) with no compiler-enforced guarantee they match,
which is precisely the kind of manual-sync failure mode TR-06
("schema-first data ordering... parsed through that schema at load time")
is designed to prevent.

## Consequences

- **Easier:** one runtime, one lockfile, one test runner, no transpile
  step; a single `bun install && bun test` gets a clean clone running.
  Types and runtime validation stay in lock-step by construction (Zod),
  removing an entire class of "the type says X but the validator allows
  Y" bugs.
- **Easier:** CI (`docs/development/ci-cd.md`) is a short, fast pipeline
  because every step (`format:check`, `lint`, `typecheck`, `test:coverage`,
  `build`, `validate`) uses the same toolchain, with no cross-tool
  version-matrix to maintain.
- **Harder:** Bun is a younger runtime than Node.js, with a smaller (though
  fast-growing) ecosystem and fewer years of production hardening.
  Behaviour of `bun:test`'s coverage engine, in particular, has already
  needed empirical verification rather than being taken on faith (see
  `docs/development/testing.md`'s note on the plural `lines`/`functions`
  threshold keys).
- **Risk and mitigation:** the risk above (Bun's relative youth, and the
  possibility of a breaking behaviour change between Bun versions
  affecting coverage/build/test output) is mitigated by pinning Bun to an
  **exact version** in CI (`bun-version` on `oven-sh/setup-bun@v2`, not a
  floating range), documented in `docs/development/ci-cd.md`'s "Action and
  tool pinning policy," with the pinned version bumped deliberately rather
  than as a side effect of an unrelated change.
