# v1.0.0 — 2026-09-05

Initial stable release of `osn-informatika-2026`.

## What this is

This repository is a typed, validated, version-controlled encoding of the
*Silabus Operasional Pembinaan OSN Informatika 2026* (v2.0, 4 September
2026) — a schema, domain model, CLI and Markdown-rendering pipeline that
turn that syllabus's structure into artefacts a mentor or programme lead
can run, not just read. The source document states, verbatim: *"Dokumen
kurikulum independen. Bukan dokumen resmi Puspresnas, IA TOKI, atau IOI."*
This repository, as a machine-readable encoding of that document, inherits
that non-affiliated status: it is authored by **Tim Riset
AhliKoding.com dari AhliWeb.com** and is not published, endorsed, or
reviewed by Puspresnas, IA TOKI, or the IOI (International Olympiad in
Informatics).

## What you get

**The corpus.** The full operational syllabus as schema-validated data and
faithful Markdown transcription:

- 28 operational weeks, organised around **10 official topic families**
- **7 phase gates** (after weeks 4, 8, 12, 16, 20, 24, 28), each with its
  own minimum-evidence requirement
- **41 references** (R1–R41), cross-checked so no citation anywhere in the
  corpus can dangle
- **7 Indonesian regulations** (§10) and **14 ISO/IEC standards** (§11)
  mapped to concrete controls

**The pedagogy and assessment model.** The §5.1 two-session weekly
template (two 120-minute sessions with five timed segments each), the
§5.2 seven-step mentor SOP, the §5.3 progressive hint ladder, the §6.1
weighted rubric (five components summing to exactly 100), the §6.2
A/B/C/D problem-status engine with its 3–7 day re-solve window, the §6.3
mentor KPI suite (seven metrics, each with an explicit "insufficient
data" state instead of crashing or returning `NaN`), the seven §7
decision playbooks, and the six-kind §13 assessment bank.

**The `osn` CLI** — six commands:

| Command | What it does |
| --- | --- |
| `osn validate` | Audits the entire corpus in one pass: schema conformance, structural invariants, and cross-file referential integrity. |
| `osn plan` | Generates a dated 28-week cohort calendar from a start date, shifting weeks around excluded holiday/exam dates. |
| `osn render` | Produces mentor-ready Markdown: a weekly plan, a checkpoint sheet, or the one-page SOP card. |
| `osn report` | Computes the KPI dashboard, postmortem error taxonomy, and scheduled re-solves from a learning-record file. |
| `osn checklist` | Renders the §14.1 cohort-readiness checklist and §14.2 operational rules, with corpus version and syllabus-check status. |
| `osn privacy-check` | Scans `data/` for direct-identifier-shaped keys — a CI-enforced governance control, not just documentation. |

## Getting started

Prerequisites: [Bun](https://bun.sh) `1.4.0` (the version this project
pins in CI — see `.github/workflows/ci.yml`).

```sh
bun install
```

A worked sequence a mentor lead would actually run before a cohort
starts — every command below was run against this release and exits `0`:

```sh
# 1. Confirm the corpus itself is sound.
bun run validate
# osn validate: corpus at <repo>/data
# OK -- 22 data file(s) validated, 0 problem(s) found.

# 2. Review the cohort-readiness checklist and operational rules.
bun run src/cli/index.ts checklist
# (or, once installed as a bin: osn checklist)

# 3. Plan a cohort calendar from a start date.
bun run src/cli/index.ts plan --start 2026-09-14
# generates the 28-week dated calendar, session dates, mini-contest
# and checkpoint markers; add --exclude and --target-stage as needed.

# 4. Render a mentor-ready weekly plan.
bun run src/cli/index.ts render weekly --week 1
# writes the week's content, outcome, both 120-minute session
# templates, the SOP reminder and the hint ladder as Markdown
# (add --out <path> to save it instead of printing to stdout).
```

Each subcommand also accepts `--help`, and `osn --version` prints the
installed version (`1.0.0`) directly from `package.json`. See
`docs/cli/README.md` for the full reference and every flag.

## What this is not

- **Not a judge.** It does not compile, run, or score submitted code.
- **Not an LMS.** It does not deliver lessons, track enrolment, or manage
  cohorts.
- **Not a student data store.** It holds no learner personal data; any
  sample data included is synthetic, and the learning-record schema
  rejects direct identifiers by construction.
- **Not an ISO/IEC certification.** The governance documents *map*
  security controls onto fourteen ISO/IEC standards — that is a
  documentation exercise, not a certification, and this repository does
  not claim to be certified to any of them.

## Known limitations and open items

- **Contact placeholders.** `SECURITY.md`, `CODE_OF_CONDUCT.md`,
  `docs/governance/privacy.md` and
  `docs/governance/incident-response.md` each carry an explicitly marked
  contact placeholder (e.g. `[SECURITY-CONTACT-NOT-YET-CONFIGURED]`,
  `[DPO-CONTACT-NOT-YET-CONFIGURED]`) that **must be filled with a real
  address or person before this repository is published or operated
  against a real cohort.** No address or person was invented to fill
  them.
- **The seeded syllabus-check log entry is a transcription record, not a
  live verification.** `data/syllabus-check-log.json`'s initial entry
  records that the corpus was transcribed from the source document; it
  does **not** represent a live check of the external OSN/IOI sources
  (R1, R2, R3, R7, R8). The next syllabus check must perform that live
  verification per `docs/operations/syllabus-check.md` before the next
  cohort cycle begins.
- **`osn report --by topic` and `--by week` do not work yet.** Grouping a
  KPI report by topic family or by week needs a `problemId` → topic
  family resolver and a timestamp → week-number resolver, neither of
  which this corpus ships (there is no such registry under `data/`, and
  week-resolution needs a cohort's own start date and excluded-days list,
  which `osn report` has no flag to supply). Both currently exit `2` with
  an explanation; `--by none` (the default) is the only grouping that
  works via the CLI today. The underlying `buildKpiReport` function is
  already generic over any caller-supplied resolver, so this is a CLI gap,
  not a domain-model one.
- **`complexitySelectionAccuracy` is a proxy, not a direct measurement.**
  This §6.3 KPI infers whether a student picked an appropriate algorithm
  for the given constraints from TLE/AC verdict patterns in the learning
  record, because the record does not capture the student's stated
  complexity reasoning directly. Read it as a proxy signal, not ground
  truth.
- **The week → topic-family mapping is an editorial inference.** The
  source syllabus's week-by-week table (§4) does not itself tag every
  week with topic-family ids; this repository's `data/weeks.json`
  `topicFamilies` field is this project's own reading of which §2.1
  rumpun each week's content belongs to, not a field transcribed verbatim
  from the source document. Referential integrity is enforced (every id
  resolves to a real topic family), but the mapping's *correctness* is an
  editorial judgment, not source text.
- **The requirements register itself lists two items as still
  "planned"** rather than "implemented": OR-12 (re-verifying the
  contributor/agent guide against the implementation at release time) and
  GR-12 (this release's own final-verification gate) — both are, by
  definition, closed out by the work this release document itself
  performs, but the register's own status column was intentionally left
  untouched by this task (see "Rules" in the governing issue) and should
  be updated as a follow-up once this release lands.
